摘 要

针对股票研究中行情数据、新闻公告、政策文件与分析结论分散的问题，本文设计并实现了一套基于大语言模型与多源数据融合的股票波动分析系统。系统按前后端分离方式部署：后端以 FastAPI 提供接口服务，PostgreSQL 负责数据持久化，Redis 用于缓存管理；前端基于 Vue 3，实现热点浏览、个股详情、分析工作台、自选股与后台管理等页面。数据接入层汇聚股票基础信息、K 线、热点新闻、个股公告和政策文档，并以统一事件模型承载不同来源材料，使其在后续报告生成中具备筛选、关联与追溯能力。

在分析流程中，系统以股票代码、主题、锚点事件和时间范围限定上下文，并在此基础上编排多智能体角色完成证据筛选与审计、假设构建以及报告归档；报告生成后，可在历史报告、证据来源、因素拆解与导出文件中回看。为支持长期跟踪，系统提供自选股自动同步，并将后台同步、分析生成等作业统一记录，便于定位异常与复盘。结合后端接口测试、前端组件测试及若干典型场景验证，账号安全、数据接入与报告生成链路的运行结果与预期一致。最后，本系统把多源金融信息整理、模型辅助分析与工程过程留痕放在同一套流程里，便于复查与维护。

关键词： 股票波动分析；大语言模型；多源数据融合；多智能体；任务追踪

ABSTRACT

To address the fragmentation of market data, news, announcements, policy documents and analysis results in stock research, a stock volatility analysis system based on large language models and multi-source data fusion was designed and implemented. A front-end and back-end separated architecture was adopted. FastAPI, PostgreSQL and Redis were used for interface services, persistence and caching, while Vue 3 was used to build pages for hot-event browsing, stock details, the analysis workbench, watchlists and administration. Stock master data, K-line records, hot news, company announcements and policy documents were integrated at the data access layer, and a unified event model was used to transform heterogeneous materials into selectable, linkable and traceable analytical evidence.

In the analysis workflow, stock code, topic, anchor event and time range were used as contextual constraints. Multi-agent roles were arranged to complete evidence selection, evidence auditing, hypothesis construction and report archiving, and the generated results can be reviewed through historical reports, evidence sources, factor breakdowns and exported files. Automatic watchlist synchronization and unified job records were introduced to trace background synchronization, report generation and abnormal states. Backend API tests, frontend component tests and scenario validation for login, analysis generation, policy synchronization, hot-event navigation and watchlist synchronization confirmed that the core functions worked as expected. The system combines multi-source financial information organization, large-language-model-assisted analysis and engineering process tracing, providing a reviewable and maintainable implementation for stock volatility research.

**Keywords:** stock volatility analysis; large language model; multi-source data fusion; multi-agent; task tracing

# 第一章 绪论

## 一、背景及意义

做股票研究时，最麻烦的地方往往不是没有数据，而是数据分得太散。价格走势在行情接口里，新闻在资讯接口里，公告和政策又有各自的来源，如果只盯着历史 K 线，很难解释一次波动背后的事件诱因。本文所实现的项目在整理需求时也遇到同样的问题，研究人员往往真正需要的不是再打开几个页面查资料，而是把事件从哪里来、关联到哪只股票、最后形成什么分析结论，连成一条能回看的链路。

从项目开发过程看，股票研究系统不能只停留在调用一次大模型这一层。它还要处理用户登录、数据同步、后台任务、运行日志、页面跳转和历史报告等细碎但必要的工作。比如一条政策文件进入 policy_documents 后，还要通过 scope='policy' 的投影进入 news_events，前端热点页和分析工作台才能沿用同一套事件消费方式。少了这些工程环节，模型生成的文字很难变成可持续使用的研究工具。

另一个容易被忽略的问题是研究过程的连续性。一次分析报告生成后，用户往往还会回头查看证据、比较不同时间的报告，或者把结果导出给他人阅读。如果系统只保留最终一段文本，而不保存事件输入、角色运行记录和任务状态，那么报告看起来完整，实际却很难复查。本文选择从工程系统角度切入，也正是因为这些看似琐碎的记录能力，会直接影响股票研究工具能否长期使用。

本文的价值主要落在工程实现上。最初整理项目时，更加关注的是怎样把股票主数据、K 线、热点新闻、个股公告、政策文档和大模型分析放到同一个应用里，但是真正写到报告生成链路时才发现，难点不止是生成一段分析。如果没有分析会话、历史报告、自选股自动化和统一任务中心，用户很难知道当前结论由哪些事件、哪些后台任务和哪些角色运行记录支撑。论文后文围绕这些可回看的工程痕迹展开，而不是把系统描述成一组互不相干的脚本。

本文避开收益率和预测准确率的论证。是因为本系统要证明的是系统功能、数据链路和测试覆盖，而不是投资效果。本文能回答的问题是，怎样用真实代码搭起一套面向股票研究的分析平台，并用配置、数据库结构和测试结果说明它确实能够运行。

## 二、国内外研究现状及分析

国内关于股票波动分析和金融文本处理的研究，近几年已经从单一价格序列逐步走向文本、情绪、知识结构和行情数据的联合使用。林建浩、孙乐轩对大语言模型在经济金融文本分析中的基本原理和应用边界做了梳理，说明公告解读、舆情研判、主题识别和知识抽取正在成为金融文本处理的重要场景<sup>\[1\]</sup>。在更具体的情感建模方向上，段魏诚、薛涛提出 FinBERT-RCNN-ATTACK 模型，用金融领域预训练表示、循环卷积结构和对抗训练提升中文金融文本情感分析的鲁棒性<sup>\[2\]</sup>。岑咏华等则利用财经新闻、股吧和博客文本构造情感变量，讨论媒介情绪与股票市场表现之间的关系<sup>\[3\]</sup>。面向股票预测任务，余传明等提出文本价格融合模型，尝试把股评文本特征和价格指标合并使用<sup>\[4\]</sup>。徐月梅等进一步将新闻情感、技术指标和行情数据引入 CNN-BiLSTM 多特征融合模型<sup>\[5\]</sup>。吕华揆等从异质性财经新闻角度分析新闻类别、情绪和市场波动之间的滞后关系<sup>\[6\]</sup>。此外，刘政昊等把金融证券数据组织成知识图谱，用实体、关系和图挖掘发现相关股票<sup>\[7\]</sup>。还有袁婧等则把投资者评论情绪、技术指标和历史交易数据放入 S_AM_BiLSTM 框架<sup>\[8\]</sup>。这些国内成果为本文提供了直接参考，即股票研究不能只看行情数值，也需要处理新闻、评论、政策、公告和证券关系等多源信息。

国外研究较早把文本因素引入市场行为解释与预测。Tetlock 以《华尔街日报》专栏为样本，讨论媒体悲观情绪与价格压力、交易量变化之间的联系<sup>\[9\]</sup>；在后续工作中，他进一步指出，公司相关新闻中的负面词比例可以作为企业基本面信号的近似刻画<sup>\[10\]</sup>。在社交媒体语料方面，Bollen 等将 Twitter 情绪序列与道琼斯指数变化进行对照分析，使社交媒体情绪成为股票研究中的常用变量之一<sup>\[11\]</sup>。方法与资源层面，Loughran 和 McDonald 强调通用词典在 10-K 等金融文本上容易产生误判，并提出更贴合金融语境的词典思路<sup>\[12\]</sup>；Schumaker 和 Chen 的 AZFinText 系统则尝试结合突发金融新闻、命名实体与机器学习用于短时预测<sup>\[13\]</sup>。在综述与边界讨论方面，Kearney 和 Liu 汇总了金融文本情绪研究的方法、数据源与经验结论<sup>\[14\]</sup>，Malo 等围绕金融短语语料与语义方向识别展开讨论<sup>\[15\]</sup>，Loughran 和 McDonald 也从会计与金融研究视角总结了文本分析的实施风险与方法边界<sup>\[16\]</sup>。这些工作共同指向一点：金融文本不只是价格序列的「注释」，它本身承载着市场预期、投资者反应以及企业信息披露的线索。

随着深度学习与多模态方法的发展，研究关注点逐渐从“是否引入文本”转向“文本、价格与结构信息如何共同建模”。Ding 等从新闻中抽取事件特征，并用神经张量网络与卷积网络研究事件驱动的预测思路<sup>\[17\]</sup>；Fischer 和 Krauss 则验证了 LSTM 在金融市场预测任务中的适用性<sup>\[18\]</sup>。针对社交媒体与价格的结合，Xu 和 Cohen 将 Twitter 文本与历史价格放入深度生成模型，用以刻画预测中的随机性与时间依赖<sup>\[19\]</sup>。在综述层面，Sezer 等统计了 2005—2019 年深度学习在金融时间序列预测中的应用，指出趋势预测仍是主要场景<sup>\[20\]</sup>，Jiang 进一步总结了近期进展并强调复现性与实现细节的重要性<sup>\[21\]</sup>。更贴近“多源融合”问题的一类工作开始同时利用价格、新闻与关系结构，例如 Cheng 等提出多模态图神经网络，在同一框架内引入历史价格、新闻文本与知识图谱关系<sup>\[22\]</sup>，Chen 等也采用新闻标题、技术指标与时间序列构建深度融合模型<sup>\[23\]</sup>。此外，Du 等将金融 NLP 的应用场景归纳为情感分析、叙事处理、预测、问答、风险管理、监管合规与可解释性等方向<sup>\[24\]</sup>，Chen 等把大语言模型用于金融新闻情绪预测，并通过领域知识与提示策略提升分类效果<sup>\[25\]</sup>。

把前述研究放在一起看，会发现现有工作更常把笔墨放在模型效果、特定语料或数据集实验上。做成一个可用的系统时，工程侧反而有几类问题绕不过去：一是行情、新闻、公告、政策等数据要持续采集并完成清洗；二是文本证据需要能与股票、事件以及分析报告建立可追溯的关联；三是大模型输出要可记录、可回看、可导出；另外，后台任务一旦失败，也得能快速定位原因。基于这一取向，本文不把重点放在收益率预测的排名比较上，也不把系统写成投资效果验证工具。本文依托本人独自开发的多源股票分析系统的真实实现，讨论多源数据与大模型分析如何在同一平台被组织起来，以及分析会话、历史归档、导出、自选股自动化与任务中心如何把一次分析延伸成可追踪的研究流程。

## 三、研究内容及目标

本文实现的系统面向研究型用户的股票波动分析流程，核心目标是把行情、新闻/公告与政策材料纳入同一条可追溯链路。系统同时处理结构化行情与非结构化文本：新闻、公告和政策文件不会只停留在页面展示，而会进入分析会话，作为报告生成的可回溯证据。工程实现上，后端采用 FastAPI + SQLAlchemy + PostgreSQL，并使用 Redis 处理缓存与部分运行时状态；前端使用 Vue 3、Vite、TypeScript 组织页面交互。为避免报告生成与自选同步阻塞 HTTP 请求，后台单独运行 Analysis Worker 与 Watchlist Worker，分别承担分析任务与自选跟踪。

围绕上述目标，本文主要处理了几条实际开发中绕不开的链路。账户部分要同时照顾普通用户和管理员，因此使用 JWT、Redis 刷新令牌、邮箱验证码、登录验证码和 IP 风控来划清访问边界。数据部分分别接入 Tushare、AkShare 以及 gov_cn、pbc、ndrc 等官方政策源，股票主数据、K 线、热点新闻、公告和政策文档先各自落库，再通过 policy_documents 与 news_events(scope='policy') 把政策信息带到热点事件页面。分析部分从 analysis_generation_sessions 开始，研究规划、证据检索、证据审计、候选假设、反向质询和最终裁决等角色结果写入 analysis_agent_runs，最终报告进入 analysis_reports。至于自选股小时同步、每日分析和 system_job_runs，则更多是为了让系统后续还能查、还能排障。

前端页面也围绕研究路径做了联动，用户可以从热点页查看「国际油价高位震荡」一类事件，再进入贵州茅台等个股页面，最后带着 topic、event_id 和股票代码进入分析工作台。分析完成后，报告可从历史列表回看，也可以导出为 Markdown 或 HTML。仓库中的后端测试、前端测试和持续集成配置用于支撑本文的功能验证，论文的讨论边界也限定在这些可检查的工程事实内。

# 第二章 需求分析

## 一、用户角色与业务场景

本项目面向的是带有研究性质的股票分析流程。用户通常会先看市场热点或股票列表，再进入个股详情页查看行情、新闻和政策线索，随后在分析工作台围绕某只股票发起一次分析。对于需要长期关注的股票，用户还会把它加入自选列表，让后台定时同步新闻或生成日报。按照这一使用路径，系统中的用户可以分为游客、普通用户和管理员三类。

### (一)游客用户

游客不需要登录就能访问公开页面，包括首页、热点新闻页、个股详情页、政策文档检索页和分析工作台的公开展示内容。这个角色更像是第一次进入系统的试用者，通常先在热点页浏览某个主题下的事件和 A 股候选股票，再点进个股详情页看看行情和相关新闻。如果继续进入分析工作台，游客可以了解报告展示形式，但不能创建私有分析会话，也不能保存个人研究记录。

### (二)普通用户

普通用户在游客能力之外拥有完整的个人账户。登录后，用户可以维护个人信息、管理自选股列表，也可以围绕一只股票创建私有分析会话。对这类用户来说，系统的重点不是查一次就结束，而是把研究对象留在系统里继续跟踪，分析工作台会通过 SSE 返回进度，报告生成后进入历史记录，必要时还能导出为 Markdown 或 HTML，然后自选页中的小时同步、每日报告、联网增强等开关，则把原本静态的关注列表变成后续任务入口。

普通用户的操作路径在项目中体现得比较具体。例如用户可以先把贵州茅台这类股票加入自选，再单独打开小时同步或每日报告，也可以从热点页带着 commodity_supply 主题进入分析工作台，让系统优先采用国际油价高位震荡等事件作为分析锚点。这样的路径比单纯输入股票代码更接近真实研究习惯，因为用户通常是从某条新闻、某个政策变化或某次市场波动开始追问原因。

### (三)管理员

管理员负责系统治理和日常维护。后台页面向管理员开放任务中心、用户管理、股票同步、政策同步和热点影响快照预热等功能。实际排查问题时，管理员最常看的不是某个业务页面，而是 system_job_runs 中的任务状态、错误堆栈和指标 JSON，表示了分析任务有没有完成、policy_sync 哪个 Provider 失败、watchlist_hourly_sync 抓到了几条新闻，这些都需要在后台留下可查记录。

股票与行情模块服务于前端的股票列表和个股详情页。系统需要支持股票基础信息分页、代码或名称模糊搜索、公司概况和行业信息查询，也要能返回日 K、周 K、月 K 等行情序列。后台同步任务负责补充股票主数据、交易日历和复权因子，避免页面每次都直接依赖上游接口。

新闻与政策模块处理的是非结构化信息。热点新闻、个股新闻和上市公司公告会进入 news_events，政策文件则先进入 policy_documents，再生成 scope='policy' 的事件投影。这样做的好处是前端不必为政策文件单独写一套展示逻辑，热点页、个股详情页和分析工作台仍然可以沿用事件查询接口。

分析工作台围绕单只股票展开。用户输入股票代码或从热点事件带入股票code、commodity_supply、evt-hot-1 这类上下文后，系统创建分析会话，通过 SSE 返回阶段进度，并把最终报告持久化到 analysis_reports。历史列表、证据回看、因素拆解和 Markdown/HTML 导出都是围绕报告后续使用设计的。

自选股自动化模块让关注列表继续动起来。用户可以添加或移除股票，也可以为每一只股票单独配置小时同步、每日报告和联网增强。Watchlist Worker 根据这些配置执行新闻抓取、行情快照生成或每日分析任务，执行结果再回到前端自选页面和后台任务中心。

后台任务中心收拢所有异步作业。分析生成、新闻抓取、政策同步、股票同步和自选自动化都会写入 system_job_runs，后台页面按任务类型、状态和时间范围筛选记录。管理员点开单条任务时，需要看到执行参数、耗时、输出摘要和错误堆栈，这比只给一个失败状态更有排查价值。

## 三、非功能需求分析

除了功能本身，系统还要照顾安全性、可维护性、可追踪性和可扩展性。股票研究系统一旦引入登录、后台任务和外部数据源，这些非功能要求就不再是附加项，而是日常使用中很容易暴露问题的部分。

安全边界主要落在两处：账户侧的身份校验，以及接口侧的访问来源约束。账户侧会在 Redis 中记录登录失败次数，达到阈值后再启用图形验证码；密码修改与重置流程需要同时携带邮箱验证码，以减少敏感操作被绕过的可能。刷新令牌保存在 Redis 中并支持撤销，用户登出后不能继续通过刷新接口获取新的访问令牌。接口侧通过 CORS 白名单限制跨域来源，并为每个请求分配 X-Request-ID 以便关联日志；在反向代理场景下，仅当可信代理配置成立时才解析 X-Forwarded-For，从而避免客户端伪造来源地址。

可维护性更多来自结构边界。后端按 auth、stocks、news、policy、analysis、watchlist、admin、market_theme 等模块拆分，修改政策同步时不应该牵动登录逻辑，调整分析流水线时也不应影响股票基础查询。数据库变化交给 Alembic 迁移脚本管理，配置项与敏感信息从环境变量或本地 .env 读取。前端则通过路由懒加载和组件拆分降低页面之间的耦合，后续新增页面时不会把整个应用重新组织一遍。

可追踪性在需求分析里容易被写成一句口号，但实际开发时很快会变成具体问题，像是分析任务挂住了，新闻抓取少了几条，或者自选股同步没有更新，管理员总要知道问题卡在哪一步。本项目里的分析生成、新闻抓取和自选自动化大多是异步执行，如果只靠控制台日志，过一段时间再排查就很被动。为此，系统把后台作业写入 system_job_runs，记录任务类型、状态、开始与结束时间、错误信息和运行指标。以 policy_sync 为例，任务指标里会留下 Provider 数量、成功源、失败源和插入更新统计，管理员看到失败记录后，至少能判断是 pbc、ndrc 这样的单个来源出了问题，还是整条同步链路没有跑起来。

这类可追踪设计在论文中不适合写成抽象口号，而要落到具体字段和页面上。system_job_runs 中的 job_type 可以区分 policy_sync、watchlist_hourly_sync、watchlist_daily_analysis 等任务，status 记录任务结果，metrics_json 保存每类任务特有的统计信息。管理员在后台打开任务详情时，可以直接看到失败原因或抓取数量。这比只在控制台打印日志更便于长期维护。

可扩展性体现在项目后续还能继续加能力，而不是每次新增都推翻原结构。政策数据源增加时，可以补充新的 Provider，分析流程需要扩充角色时，可以在多 Agent 流水线中加入新的环节，报告交付形式变化时，也可以围绕已有导出服务继续扩展。前端通过 Pinia、路由参数和页面局部状态承接这些变化，避免把业务逻辑全塞进单个页面组件。

# 第三章 相关技术

## 一、后端开发选型

本项目选择 FastAPI，主要是因为它和现有后端形态贴合，接口多、数据模型多，而且不少链路需要异步访问数据库或外部服务。FastAPI 基于类型注解和 Pydantic 模型组织请求、响应结构，前端联调时可以直接参考自动生成的 OpenAPI 文档。对本系统而言，这比手写散乱的接口说明更稳妥。

在代码结构上，项目把鉴权、股票、新闻、政策、分析、自选与后台管理等接口统一挂在 FastAPI 路由下，但路由层仅负责 HTTP 请求解析与响应封装，核心数据处理放在 service 或 repository。Analysis Worker 与 Watchlist Worker 虽然不是 HTTP 服务，也复用同一套服务层函数，使 API 请求与后台任务在业务口径上保持一致。

uv 在项目中承担统一运行入口的角色。依赖安装、数据库迁移、测试执行和开发服务器启动都可以通过 uv run 进入同一套 Python 环境。这样处理的好处很实际，即本地开发和持续集成更容易保持一致，排查测试问题时也不必先猜测当前机器到底用了哪个虚拟环境。

## 二、前端开发选型

前端选择 Vue 3，是因为本系统的页面虽然不算特别多，但状态关系比较密，像是热点页要保存主题和锚点事件，个股详情页要联动行情和新闻，分析工作台还要同时处理进度、历史报告、证据视图和导出操作。组合式 API 让这些状态可以按功能拆开，而不是都堆在一个庞大的组件选项对象里。

前端以 Vue 单文件组件组织页面结构，包括首页、热点页、个股详情页、分析工作台、自选页与后台管理页。跨页面的研究上下文通过 Vue Router 的 query 参数传递，例如从热点页跳转到分析工作台时会携带 topic、event_id、event_title、source 等信息。Pinia 仅维护需要全局共享的状态（如登录用户、自选列表、策略中心缓存），页面内部的临时交互状态仍保留在组件中，以避免全局 store 过度膨胀。

前端构建采用 Vite 作为开发与构建工具，本地调试时可直接利用热更新能力。TypeScript 用于约束接口返回值、Pinia 状态、组件属性与路由参数；以分析报告为例，anchor_event_id、structured_sources、factor_breakdown 等字段在前端均有明确类型约束。Element Plus 主要承担表格、表单、弹窗等基础组件，Motion 仅在少数页面切换时提供过渡动效，以增强交互反馈。

## 三、数据库开发选型

PostgreSQL 在本项目里不是单纯的存数据工具，而是系统的数据真相源。用户、股票、行情快照、新闻事件、政策文档、分析会话、分析报告、自选配置和后台任务都落在关系型结构中。股票研究链路需要频繁根据股票代码、事件、报告和任务记录做关联查询，关系型数据库在这里比零散文件或纯缓存更合适。

analysis_generation_sessions、analysis_reports 和 analysis_agent_runs 三张表就是典型例子。一份报告不只保存最终正文，还要追溯它属于哪次会话、用了哪些事件、每个角色输出了什么内容。PostgreSQL 的事务和关联查询能把这些关系稳定保存下来，也方便后台页面按任务、股票或报告维度回看。

SQLAlchemy 负责把 Python 模型和数据库表连接起来。项目使用异步会话配合 asyncpg 驱动，服务层执行查询、插入和更新时不需要直接拼接大量 SQL 字符串。对开发者来说，模型文件能直接反映 users、news_events、policy_documents、system_job_runs 等表的字段边界，后续维护更容易。

数据库结构的演进交给 Alembic。system_job_runs、policy_documents、analysis_agent_runs 等表并不是一次性写完的，而是随着任务中心、政策同步和多 Agent 运行记录逐步加入。迁移脚本把这些变化留成版本记录，API 和 Worker 启动时再做 schema 校验，避免代码已经使用新字段而数据库还停在旧结构。

系统在启动阶段保留了 schema 补齐与校验逻辑。开发环境下，若数据库或 schema 不存在，可按配置自动完成初始化；进入正式校验模式后，若迁移版本与代码要求不一致，服务会直接启动失败，而不是在表结构不完整的情况下继续运行。该策略并不复杂，但对多进程架构较关键：API、Analysis Worker、Watchlist Worker 共用同一套表结构，结构不一致会导致隐蔽的运行时问题。

## 四、数据缓存选型

本项目缓存使用的是Redis ，Redis是一种基于内存的键值存储系统，因为它的微秒级的读写延迟和丰富的数据结构支持，使它被广泛用于缓存、会话存储和分布式锁等场景。在本项目中主要依靠Redis作为缓存使用，而Redis 的数据持久化选项允许在内存性能与数据可靠性之间取得平衡，使其既可以作为纯缓存使用，也可以用于存储需要短时保留的运行状态信息，所以其很符合本项目的需求。

Redis 主要处理短生命周期和高频访问的数据。本项目不把核心业务数据放在 Redis 中长期保存，而是让它承担刷新令牌、验证码、登录失败计数、分析临时进度和部分热点查询缓存等职责。

这种分工比较清楚，其中PostgreSQL 保存必须追溯的事实，Redis 保存过期后可以丢弃或重新生成的状态。验证码和登录失败计数适合设置过期时间，热点新闻列表和行情快照适合短期缓存，避免页面重复刷新时不断访问上游数据源或数据库。即便 Redis 中某条缓存失效，系统仍能回到 PostgreSQL 或外部接口重新取数。

## 五、数据来源

股票研究需要同时接触结构化行情和文本信息，单一数据源很难覆盖完整链路。本项目因此把数据接入拆成几类，Tushare 负责更偏结构化的股票基础信息和行情序列，AkShare 负责新闻和公告等资讯，政策 Provider 则处理官方文件。

Tushare 返回的数据会映射到 stock_instruments、stock_kline_bars、stock_daily_snapshots、stock_trade_calendars 和 stock_adj_factors 等表中。前端股票列表、个股详情和 K 线图主要依赖这些本地记录，而不是每次打开页面都临时请求上游接口。

AkShare 更适合补充文本侧信息，本项目用它获取热点新闻、个股相关新闻和部分公告事件。入库后，这些内容统一进入 news_events，并通过 scope 字段区分 hot、stock、announcement 等来源，供热点页和分析工作台按条件读取。

政策数据源差异更大，所以本项目没有把抓取逻辑写成一个大函数，而是拆成 gov_cn、pbc、ndrc、miit、csrc、npc 等 Provider。每个 Provider 产出标准化种子，再由统一流程清洗正文、提取附件、去重并写入 policy_documents。为了让政策也能出现在热点影响面板和分析证据中，系统会同步生成 news_events 中的 scope='policy' 投影记录。

## 六、Agent 分析实现

本项目使用大模型，不是为了替代行情计算，而是为了处理文本归纳和研究报告组织这部分工作。新闻、公告、政策文件本身并不天然形成结论，需要把它们按股票、主题和事件锚点重新整理，再转成用户能阅读的分析报告。

调用层没有写死某个厂商或具体模型版本，而是通过 OpenAI 兼容 SDK 和可配置网关地址发起请求。这样一来，后端服务只关心请求结构和返回结果，不需要把业务逻辑绑在某个模型名称上。以后如果切换云端服务或本地推理服务，改动主要集中在配置和调用适配层。

在一次完整分析中，系统不会只把所有材料扔给模型后等待一段文本。当前流水线把任务拆成研究规划、证据检索、证据审计、候选假设、反向质询和最终裁决等角色。每个角色的输入快照、输出载荷、状态、模型参数和来源引用都会写入 analysis_agent_runs。这样生成的报告虽然仍然依赖大模型，但至少可以回头查看每一步用了哪些证据、哪一步给出了什么判断。

这里有一个实现上的取舍，虽然多 Agent 会让运行链路变长，也会增加数据库记录数量，但它换来的是过程可解释性。对于股票研究场景，这一点比快速返回一段顺滑文字更重要。若报告中出现某个风险提示，用户可以回到 Sources 视图或 Pipeline 视图查看它来自哪条新闻、哪份政策，或者是哪一个角色在中间环节提出的判断。

报告来源的整理也没有完全交给模型自由发挥。后端会把入选事件整理成 structured_sources，并在来源项中保留 provider、scope、event_id、published_at 等信息。如果材料来自政策投影，来源仍能继续指回 policy_documents。本文认为这类字段看上去虽然不如模型回答醒目，却是报告能否复查的关键。用户阅读报告时，真正关心的不只是结论写得是否流畅，还会追问这句话到底来自热点新闻、上市公司公告，还是某份政策文件。

本项目中对提示词也做了比较克制的处理。系统会把最新行情快照、候选事件、锚点事件和角色前序输出放进上下文，但不会在提示词里承诺预测收益或给出确定性投资建议。对本文而言，需要写清楚这个边界，即大模型在这里承担的是归纳、比较和报告组织工作，而不是被包装成一个可以单独决定买卖的黑箱模型。

# 第四章 架构设计

## 一、系统架构

从一次用户操作看系统架构会更清楚。用户在热点页看到国际油价高位震荡，点进 股票 并发起分析，前端只表现为页面跳转和一次生成请求，后端却要完成登录态校验、股票与事件查询、分析会话创建、进度推送和报告归档。PostgreSQL 保存用户、股票、新闻、政策、分析报告、自选配置和任务运行记录，Redis 则处理刷新令牌、验证码、登录失败计数和短期缓存。前后端分离并不是为了形式上分层，而是让页面交互、业务服务和持久化记录各自有明确落点。

本项目另外拆出了 Analysis Worker 和 Watchlist Worker。这样做的原因比较实际，因为报告生成和自选股同步都可能耗时，若全部塞在 HTTP 请求里，页面很容易长时间等待。Analysis Worker 领取待处理会话并执行多 Agent 分析，Watchlist Worker 按用户配置处理小时同步和每日报告。两类 Worker 复用 API 服务层代码，并把任务状态写入 system_job_runs。用户看到的是发起分析或开启同步两个按钮，背后其实是一组 API、Worker、数据库和缓存共同完成的异步流程。

运行时管理方面，API、Analysis Worker 与 Watchlist Worker 三个入口在启动时都会执行同一套数据库结构校验/补齐逻辑，确保三端连接的是一致的数据库结构。开发环境下，系统可按配置自动创建数据库与 schema，并执行 Alembic 迁移；在校验模式中，一旦数据库版本不满足代码要求，服务会立即失败并输出对应错误提示。借助这一机制，本地开发、后台任务与持续集成的数据库结构语义能够保持一致。

## 二、核心数据流

系统的数据流可以按五条主线理解，股票行情、新闻公告、政策文档、分析报告和自选股自动化。这样划分比单纯按页面说明更清楚，因为同一个页面往往会同时消费多类数据。

这些数据流之间不是彼此隔离的。热点页会同时读取新闻、政策投影和候选股，而个股详情页既展示行情，也展示相关新闻和公告，此外分析工作台还会把股票代码、topic、anchor_event_id 等参数带到后端，让分析服务筛选更贴近当前主题的事件。本文在图和正文中保留这些链路，是为了说明系统并不是几个页面的拼接，而是一套围绕研究上下文流转的工程实现。

### (一)股票数据流。

股票基础信息和行情数据主要来自 Tushare。同步任务会拉取股票主数据、交易日历、复权因子和日周月 K 线，映射后写入 stock_instruments、stock_daily_snapshots、stock_kline_bars 等表。前端打开股票列表或个股详情页时，后端优先读本地数据库，如果某段 K 线缺失，再回源补齐并更新缓存。这样页面不用每次都等外部接口返回，也能在数据不足时补上缺口。

### (二)新闻与公告数据流。

新闻事件覆盖热点新闻、个股新闻和上市公司公告。抓取任务按批次记录，正文统一写入 news_events，scope 字段区分 hot、stock、announcement 等来源。入库前会按标题、发布时间等信息去重，避免同一新闻在热点页和个股页重复出现。后台任务的成功、失败和抓取数量会写进 system_job_runs，后续排查时能找到对应批次。

### (三)政策数据流。

政策链路先独立保存，再和新闻事件体系汇合。各 Provider 从 gov.cn、中国人民银行、国家发展改革委、工业和信息化部、中国证监会、全国人大等来源抓取文件列表和正文，统一转成 PolicyDocumentSeed，再清洗 HTML、提取附件、补齐来源并按 URL 哈希去重。原始政策写入 policy_documents，为了让热点页和分析工作台继续按事件模型消费，系统再写入一条 news_events 中的 scope='policy' 投影。政策数据流的结构示意如图4-2所示。

### (四)分析数据流。

分析数据流主要解决两个问题，其一是上下文不能丢，过程也不能只留在内存里。用户在工作台选择股票并发起分析后，后端先写入 analysis_generation_sessions，记录股票代码、主题、锚点事件和会话状态。随后服务会按照股票代码和 anchor_event_id 筛选新闻、公告、政策事件，再决定当前请求内联执行，还是交给 Analysis Worker。其二是各角色的输入和输出进入 analysis_agent_runs，摘要、因素权重和风险提示进入 analysis_reports。前端通过 SSE 看到阶段进度，报告完成后，历史列表读取的是数据库中的归档结果，而不是浏览器里临时保存的一段文本。

以中国海油为例：用户从热点页携带“国际油价高位震荡”等锚点事件进入分析工作台后，后端会优先将 anchor_event_id 对应事件纳入候选证据集合，并再按 topic 过滤补充相关事件。报告写入 analysis_reports 时，会同时保存 anchor_event_id、anchor_event_title、structured_sources 等字段；因此前端切换历史报告时，能够复原当时的事件语境与来源信息。

### (五)自动化数据流。

自选股自动化以 user_watchlist_items（用户关注表）为中心。用户为某只股票开启小时同步后，Watchlist Worker 会按扫描周期触发新闻增量抓取，并生成当日行情快照；若开启每日报告，Worker 还会在每日窗口检查当天是否已生成过报告，从而避免重复创建分析会话。每次 watchlist_hourly_sync 或 watchlist_daily_analysis 都会写入 system_job_runs，管理员可通过任务记录查看执行是否成功以及本轮抓取数量。

## 三、模块划分

后端模块按业务边界拆分为 auth、stocks、news、policy、analysis、watchlist、admin 和 market_theme 等包。其中auth 处理登录、令牌和密码安全，stocks 管理股票基础信息和行情，news 负责热点新闻、个股新闻与公告，policy 处理政策 Provider、政策主表和事件投影，analysis 承接会话、多 Agent 编排和报告生成，watchlist 管理自选股及自动化配置，admin 汇总用户管理、任务监控和同步操作，market_theme 维护热点主题和候选股关系。路由层尽量薄，复杂逻辑放在服务层或仓储函数中，这样后续修改某个模块时影响面更可控。

前端页面按用户浏览路径组织。首页提供股票入口，热点页围绕事件主题聚合新闻、候选股和政策依据，个股详情页展示行情、基础信息、新闻和公告，分析工作台负责会话创建、进度展示、历史报告和导出，自选页处理个人关注列表，后台页面留给管理员查看任务与同步数据。跨页面上下文通过路由参数传递，例如热点页可以把 topic、event_id 和 event_title 带入分析工作台，让分析从一开始就带着具体事件语境。

## 四、数据库设计

数据库按业务域组织，主要覆盖用户与权限、股票与行情、新闻与事件、政策文档、分析工作台、自选股配置和后台任务管理。这里的划分并不是为了凑模块，而是为了让后续查询和维护能找到明确落点。

数据库按业务域组织，便于后续查询与维护。用户域以 users 表为入口，保存账户、加密口令、邮箱、用户等级以及登录失败计数等字段。股票域以 stock_instruments 为主表，并关联 stock_daily_snapshots、stock_kline_bars、stock_trade_calendars、stock_adj_factors 等表，以覆盖日行情快照、多周期 K 线、交易日历与复权因子。新闻事件域以 news_events 为核心，通过 scope 区分热点、个股、公告与政策投影，抓取批次则记录在 news_fetch_batches。政策域以 policy_documents 作为官方文件主表，附件信息落在 policy_document_attachments。

分析工作台域由 analysis_generation_sessions、analysis_reports 和 analysis_agent_runs 组成。会话表记录一次分析从 pending 到 completed 的状态变化，报告表保存最终摘要、风险点和因素拆解，角色运行表保留多 Agent 各环节的中间结果。自选股域通过 user_watchlist_items 关联用户与股票代码，并保存 hourly_sync_enabled、daily_analysis_enabled 等开关。任务管理域集中在 system_job_runs，分析生成、新闻抓取、政策同步和自选自动化都在这里留下运行状态、耗时和错误详情，具体每张表的实际意义可以参考表 4-1 ，表中大致的解释了使用的比较多的核心表的用处。

# 第五章 系统实现

## 一、用户安全实现

账户体系是系统的入口，也决定了个人研究记录和后台管理能力的边界。本项目提供注册、登录、令牌刷新、登出、密码修改、密码重置和当前用户信息查询等接口，前端对应登录页、注册页和个人中心页面。

令牌管理采用短访问令牌 + Redis 刷新令牌的方式。JWT 访问令牌用于普通接口鉴权，刷新令牌保存在 Redis 中，便于在登出或风险场景下直接撤销。/api/auth/refresh 每次都会生成新的访问令牌和刷新令牌，旧刷新令牌随即失效，减少长期令牌被复用的风险。

邮箱验证码用于注册、修改密码和忘记密码。注册前先发送验证码，提交注册时带回六位数字，修改密码时还要同时校验当前密码、新密码和邮箱验证码。忘记密码流程则分为发送重置邮件、验证码校验和设置新密码。后端对外返回统一格式，不直接暴露某个邮箱是否已经存在，避免把接口变成账号枚举工具。

系统按“账号 + IP”维度在 Redis 中记录登录失败计数，并设置过期时间；连续输错后，下一次登录需要先通过图形验证码。验证通过并登录成功后，对应失败计数会被清理。若系统部署在反向代理之后，仅当请求来自可信代理且配置成立时才解析 X-Forwarded-For，否则仍以直连来源地址为准。

接口层面的跨域限制采用 CORS 白名单，相关安全配置从环境变量或配置文件加载。系统在中间件为每次请求生成 X-Request-ID，并在日志中沿用该标识，用于关联一次完整调用。前端发生接口异常时，页面保留该 ID，便于在后端日志中定位对应请求。

## 二、股票数据实现

股票与行情模块把外部证券信息沉淀到本地数据库。stock_instruments 保存股票基础信息，stock_daily_snapshots 记录日行情快照，stock_kline_bars 存多周期 K 线，stock_trade_calendars 和 stock_adj_factors 分别承担交易日历与复权因子数据。

首次部署时，系统需要先执行全量同步，把 A 股基础信息写入 stock_instruments，并补入一定范围内的 K 线记录。日常运行中，后台任务只更新有变化的数据，例如名称、上市状态、最近交易日 K 线等。这样可以减少全量重抓带来的等待时间，也避免频繁消耗上游接口额度。

查询时先查 PostgreSQL，再看 Redis 缓存，必要时才回源。以前端请求某只股票 K 线为例，如果本地已经有目标周期和时间范围的数据，就直接返回，如果缺失部分交易日，再向 Tushare 补齐，并把结果回写数据库和缓存。股票列表、个股详情和交易日历这些高频请求会设置带过期时间的缓存键，减少重复读库。

stock_daily_snapshots 是自选股长期跟踪的基础。收盘后，Watchlist Worker 或同步任务会记录自选股当日收盘价、涨跌幅和成交量等指标。后续生成日报时，分析模块不用重新猜测当天行情状态，可以直接读取快照。

## 三、多源信息实现

新闻和政策的融合是本系统比较关键的一段。本项目没有把政策文件简单当作一类新闻，也没有让前端为政策单独开一条完全不同的链路，而是采用政策主数据独立保存、事件侧生成兼容投影的做法。

news_events 是事件统一入口。scope 字段区分 hot、stock、announcement 和 policy，热点新闻与个股新闻主要来自 AkShare，公告数据来自 Tushare 相关接口。news_fetch_batches 记录抓取批次、来源、时间和成功失败数量，后续如果页面出现重复新闻或缺失新闻，可以回到批次记录排查。

政策模块麻烦一些，因为各官方站点的页面结构和正文抽取规则并不一致。本项目把 gov_cn、pbc、ndrc、miit、csrc、npc 等来源拆成独立 Provider，每个 Provider 返回标题、正文、发布时间、来源和附件链接等标准化种子。调度层再统一做 HTML 清洗、空行压缩、来源补全和附件校验，把差异挡在 Provider 这一层。

归一化后，系统按 URL 哈希去重。新增政策写入 policy_documents，附件进入 policy_document_attachments，同时写入 news_events 中的 scope='policy' 记录，标题和摘要来自政策主表，source_id 指回 policy_documents。前端看到的是一个可参与热点联动的事件，后端保留的却是完整政策原文和附件关系。

政策同步任务的结果也会写进 system_job_runs.metrics_json，包括 Provider 数量、原始抓取条数、归一化条数、插入更新条数、去重条数以及失败来源。管理员不需要只看一个失败标签，可以继续定位到底是 pbc、ndrc 还是其他 Provider 出了问题。

## 四、多 Agent 分析实现

分析工作台承担从发起分析到查看报告的主流程。后端围绕三张表组织，analysis_generation_sessions 保存会话元数据和状态，analysis_reports 保存最终报告，analysis_agent_runs 保存多 Agent 每个角色的中间过程。这个设计让报告不是孤立文本，而是能追溯到会话和角色运行记录。

用户在工作台选择股票并发起报告生成时，后端会先创建 pending 状态的分析会话，记录 ts_code、topic、anchor_event_id 以及触发来源等元数据。随后可选择在当前 HTTP 请求内联执行，或交由 Analysis Worker 异步处理；但无论采用哪种方式，会话更新、报告写入以及角色运行记录的落库口径保持一致。

本项目的功能型多 Agent 流水线并不是为了把角色名列得更多，而是为了让报告生成前多几道检查。一次分析会经历研究规划、证据检索、证据审计、候选假设、反向质询和最终裁决等环节，但并不是每个环节都直接面向用户输出正文。有些角色只负责把材料整理清楚，有些角色则负责挑出时间冲突、来源不稳或证据不足的内容。各角色返回后，后端把输出载荷写入 analysis_agent_runs，并把必要信息交给下一环节。这样做会让链路变长，却能减少报告直接采纳低可信材料的风险。

事件筛选是分析流程中比较关键的前置步骤。系统不会无限制地把所有新闻都塞进提示词，而是结合股票代码、主题、锚点事件和时间窗口挑选候选材料。锚点事件会被放在更靠前的位置，同一 cluster_key 或逻辑重复的事件会被去重。这个处理能减少提示词噪音，也能让报告更贴近用户从热点页带来的问题。

所有角色结束后，最终裁决角色整合摘要、因素权重、风险提示和证据来源，写入 analysis_reports，并把会话状态改为 completed。分析过程中，前端通过 text/event-stream 接收阶段状态和文本片段，用户能看到进度变化，而不是面对一个长时间空白页面。具体流程参考图5-1分析任务流程图。

报告生成结束后，系统会刷新 fresh report 缓存，以便用户在短时间内重复打开同一股票与事件组合时直接复用最新结果。该缓存仅用于减少重复生成的等待与调用成本，不替代数据库归档；若用户主动点击刷新分析，则会绕过已有结果重新发起会话。

在实现过程中，报告生成越像实时对话，后端越需要把每一步落成稳定记录。前端看到的是 SSE 推来的阶段文本，例如正在筛选事件、正在执行证据审计、正在整理最终报告，数据库里对应的却是会话状态、角色计数、活动角色和心跳时间。若浏览器中途刷新，页面不能只依赖内存里的进度条，而要能重新读取 analysis_generation_sessions 和已有报告状态，把用户带回当前会话。

历史报告切换也是同一思路。分析工作台不只是加载 report_id 对应的正文，还要把 anchor_event_title、structured_sources、factor_breakdown 和角色流水线摘要一起恢复出来。这样用户从国际油价高位震荡进入中国海油分析后，即使隔一段时间再打开历史记录，也能看到当时为什么选择这组证据，而不是只剩下一段脱离上下文的 Markdown 文本。

图5-1 分析任务流程图

报告生成后不会只停留在当前页面。用户可以在历史报告中回看同一只股票的过往分析，也可以导出 Markdown 或 HTML 文件。对研究人员来说，这一点比较实用，一次分析的结论可以进入个人笔记、课程作业或团队讨论材料，而不是只能在页面上临时阅读。

当前前端还提供证据视图、因素视图、Pipeline 视图和 Sources 视图。用户切换历史报告时，不只看到摘要，还能继续查看证据事件、因素拆解和角色级输出摘要。这种设计保留了报告背后的过程信息，尤其适合回头检查某个结论为什么会出现。

## 五、自动化任务实现

自选股模块把用户关注的股票从静态列表扩展成持续任务。user_watchlist_items 每条记录关联一个用户和一只股票，hourly_sync_enabled、daily_analysis_enabled 等字段决定是否参与小时同步和每日报告。

Watchlist Worker 是独立的 Python 进程。它按周期扫描开启小时同步的记录，触发新闻增量抓取，并把行情快照写入 stock_daily_snapshots。收盘后，Worker 再处理开启每日报告的股票。如果当天还没有报告，就自动创建分析会话，复用分析模块完成日报生成。创建前会检查 analysis_reports，避免同一股票同一交易日重复生成。

自选股自动化的难点在于自动不等于重复执行。Worker 每轮扫描都要判断当前记录是否启用、上次执行时间是否满足间隔、当日是否已有报告，以及新闻抓取结果是否已经入库。任务成功或失败都会写入 system_job_runs，前端自选页和后台任务中心才能看到这次同步到底发生了什么。

统一任务中心的底层表是 system_job_runs。它需要同时容纳 analysis_generation、news_fetch、policy_sync、stock_sync、watchlist_hourly_sync、watchlist_daily_analysis 等任务类型。每条记录保存任务类型、状态、触发来源、关联实体、开始结束时间、耗时、错误堆栈和 metrics_json。后台页面读取这些记录后，以分页表格展示最近任务，并支持按状态、类型和时间筛选。

管理员点开任务详情时，可以看到完整错误信息和指标数据，在任务摘要页面中，也可以快速判断近期任务是否集中失败。任务中心在这里不只是任务列表，更像后台治理和故障定位的入口。

## 六、前端实现

前端页面联动要解决的是研究语境丢失问题。用户从热点页看到某个事件后，不应在分析工作台里重新输入同样的信息。Vue Router 因此承担上下文传递工作，下游页面读取参数后，调整默认股票、事件筛选和报告请求范围。

为了避免路由参数过度脆弱，页面还要处理缺省情况。例如只传入 ts_code 时，分析工作台仍然可以按普通股票分析加载，传入 event_id 但没有 event_title 时，页面会尽量从事件列表中补齐显示文本。如果历史报告中已经有 anchor_event_title，则优先展示报告归档时保存的标题。这样处理后，页面联动不会因为少一个查询参数就中断。

以热点页到分析工作台为例，用户在热点页选择 commodity_supply 主题后，影响面板可能展示国际油价高位震荡和一组候选股票。点击中国海油旁的分析按钮，页面跳转到分析工作台，同时带上股票代码、主题和锚点事件。工作台初始化时读取这些参数，把事件预填到筛选器里，后端收到请求后，也会优先把 anchor_event_id 对应事件放入分析上下文。

页面状态由 Pinia 和组件内部响应式状态共同管理。authStore 保存登录态和用户信息，策略中心等跨页面缓存也可以放在 store 中，主题上下文、事件锚点、当前报告视图这些变化快、页面相关性强的数据，则留在具体页面内维护。这个分工能避免所有状态都挤进全局 store。

前端还处理了一些容易影响体验的细节。自选按钮在个股详情页和自选页之间保持同步，点击后先做乐观更新，如果后端失败再回滚并提示。后台管理页面通过路由守卫限制，非管理员访问 /admin 会回到首页。页面组件采用懒加载，减少首屏一次性加载内容。这些细节不显眼，但会直接影响系统是否顺手。

# 第六章 系统测试

## 一、测试环境与测试策略

本项目同时保留本地测试和 GitHub Actions 测试。后端使用 Pytest，前端使用 Vitest。持续集成中会依次安装依赖、准备数据库、运行后端测试、运行前端测试并执行前端构建。这里的测试目标不是压测，也不是证明收益，而是确认主要功能链路不会在日常修改中被破坏。

后端测试依赖 Python、PostgreSQL、Redis 以及 Alembic 迁移。持续集成环境会启动独立的 PostgreSQL 与 Redis 服务，使路由、服务和集成测试在更接近运行时的前提下执行。前端测试依赖 Node.js、Vite 与 jsdom 提供的页面环境，重点验证组件渲染、路由守卫、接口包装与关键交互。

测试策略以功能验证与场景验证为主，重点关注四类检查：接口返回是否满足前端消费；服务层关键写库是否发生且口径一致；异步任务是否在 system_job_runs 留下记录；页面跳转时研究上下文是否能被正确恢复。

## 二、后端测试

后端测试没有只停留在函数调用层。当前仓库采集到 332 个后端测试项，覆盖认证安全、股票行情、新闻政策、分析工作台、自选自动化和后台管理。执行前会准备数据库结构，Redis 也参与验证码、刷新令牌和运行态缓存相关测试。这样做虽然比纯单元测试麻烦一些，但能顺手检查数据是否真的进入对应表。

不少后端测试是围绕数据库状态写的。分析相关测试不只看接口返回，还会回查会话表、报告表和角色运行表，政策同步测试会同时看 policy_documents、news_events 和 system_job_runs，自选股测试则会检查 user_watchlist_items 中的配置有没有触发对应 Worker 行为。本文更愿意保留这类检查，因为系统真正容易出错的地方，往往不是 HTTP 状态码，而是某个表没有写、某个任务没有留下记录。

认证模块的测试重点放在安全边界是否闭合。测试会先连续输错密码以触发登录验证码挑战，再在提供正确验证码与账号密码后登录，并检查 Redis 中对应账号与 IP 的失败计数是否被清理。密码修改与重置分支会携带邮箱验证码，以覆盖二次校验逻辑；刷新令牌则分别验证有效刷新、过期刷新与撤销后刷新三种路径，确认 Redis 中的刷新令牌状态会影响接口返回。

股票模块一边检查同步，一边检查查询。同步流程会把 Tushare 返回的股票主数据写入 stock_instruments，已有股票则更新字段而不是重复插入。查询侧关注列表分页、个股详情、K 线周期筛选和缓存策略。为了避免只测顺利路径，测试中也会让上游接口返回异常，看服务层能否走到降级分支。

新闻与政策部分，本文重点看写库结果。政策同步跑完后，policy_documents 里要有政策主数据，news_events 中也要出现 scope='policy' 投影，system_job_runs 里还应留下 policy_sync 任务，指标 JSON 能说明各 Provider 的抓取情况。热点影响面板则按主题读取候选股和政策文档，测试时会顺着这个返回结果看前端是否有足够内容可以展示。

分析模块的测试从会话创建开始：创建会话后，继续检查会话状态是否更新，报告是否写入 analysis_reports，角色运行结果是否进入 analysis_agent_runs。导出接口分别验证 Markdown 与 HTML 两种格式，保证已归档报告可从统一入口输出。

自选自动化模块会在 user_watchlist_items 中准备一条开启小时同步的记录，然后手动触发 Watchlist Worker 扫描。扫描后检查是否产生 watchlist_hourly_sync 任务，以及对应股票是否触发新闻抓取和快照生成。每日报告分支还会检查同一只股票同一交易日不会重复生成报告。

后台任务中心的测试会先在 system_job_runs 中放入不同类型、不同状态的记录，再调用列表、筛选和详情接口。这里重点看管理员能否按状态找到失败任务，点开后能否看到错误堆栈和 metrics_json，而不是只看到一条模糊的任务名称。

### (五)自动化同步测试

自选小时同步场景先在 user_watchlist_items 中准备一只开启 hourly_sync_enabled 的股票，然后手动触发 Watchlist Worker 的一轮扫描。扫描后主要看三处，news_events 是否新增该股票近一小时的新闻或公告，stock_daily_snapshots 是否写入当日行情快照，system_job_runs 是否出现 watchlist_hourly_sync 任务并记录抓取数量。还需要再跑一轮扫描，确认短时间重复执行不会把同一批新闻重复写入。参考图6-7。

本项目在这里没有把任务成功简单理解成 Worker 没报错就可以。而是把前端和数据库放在一起看，自选页中的同步状态要能反映后台任务结果，任务中心要能按 resource_key 找到对应股票，新闻和快照表里也要出现这轮扫描留下的数据。如果只看控制台日志，很容易忽略重复抓取、状态未回写或前端列表没有刷新的问题。这个场景虽然不复杂，却能比较集中地暴露自选自动化链路是否真的闭合。

# 第七章 总结

本文基于自研多源股票分析系统的实际实现，给出一套“多源数据融合 + 大模型分析”的工程化落地方案。整体结构采用前后端分离并配合多进程协同：数据层沉淀股票、新闻、公告与政策文档；分析层围绕会话生成可归档、可导出的报告；自选股与任务中心负责后续跟踪与运行记录。

本项目已经实现的功能有账户安全、股票查询、热点事件、政策同步、分析工作台、自选自动化和后台任务管理已经形成可运行的主链路。后端测试、前端测试、持续集成配置和 system_job_runs 任务记录，也为后续维护留下了基本抓手。本文能得出的结论仍然限定在工程实现层面，不延伸到投资收益或预测精度证明。

目前还存在处理不到位的地方，像是政策正文抽取仍然依赖各 Provider 的页面结构。一旦官方页面改版，正文、附件或发文机关字段就可能抓不完整。主题与候选股之间的映射也还需要更多真实数据积累，不能只靠少量关键词长期维持。报告交付目前主要是 Markdown 和 HTML，如果后续要用于更正式的研究材料，还需要继续补导出格式和归档规则。

如果继续迭代，会先补两件事。第一件是数据质量，尤其是政策正文清洗、公告去重、主题识别和候选股关联，尽量减少数据进来了但解释不了的情况。第二件是研究过程管理，包括报告版本、证据引用展示，以及任务失败后的重试策略。模型本身仍适合放在可替换的接口层，不把项目实现绑定到某个具体模型版本上，灵活适应多种接口，增加可扩展性。
